# VSDD 工作流与质量门禁（中文版）

## 工作流状态

`intake → capability-mapped → specified → architecture-ready → planned → implementing → verifying → converged → archived`

阶段代表变更成熟度，不是仅凭文件存在就自动通过的检查。

| 阶段 | 必须形成的结果 | 核心评审 |
|---|---|---|
| intake | 来源明确的 Feature brief、范围和未知项 | 目标/价值是否正确？ |
| capability-mapped | 有证据的复用、扩展、新建或拒绝决策 | 既有能力是否已检索？ |
| specified | 可观察行为和验收场景 | 客户行为是否明确、可测试？ |
| architecture-ready | 系统需求、职责分配、接口、架构决策 | 分配是否合理并符合真实平台约束？ |
| planned | 软件需求、任务、测试计划和追溯关系 | 任务是否能落到真实仓库和测试？ |
| implementing | 小型垂直切片的代码与测试修改 | 实际 diff 是否在批准范围内？ |
| verifying | 实际执行的测试与分析证据 | 判据、环境和结果是否可复现？ |
| converged | 无未处置的差距，追溯和审批完整 | 批准意图是否与实际交付一致？ |
| archived | 已批准的变更快照 | 基线同步和归档是否可审计？ |

## 出现差距时如何迭代

1. 记录真实现象：测试失败、行为差异、接口变化或缺失证据。
2. 找到负责该语义的工件：产品意图、Feature Spec、Capability、系统架构、软件需求、实现或测试。
3. 形成变更提案，不静默修改已批准基线。
4. 沿追溯关系识别受影响的下游项，并标记为仍然有效、待复核、已失效或不适用。
5. 先更新并审批上游，再按依赖顺序刷新下游工件。
6. 实现最小垂直切片，重新执行受影响验证。
7. 重新做 Converge；若仍有差距，就继续循环。

## 质量门禁检查

### 产品与 Feature Spec
- 来源、范围、非目标、行为和验收条件明确。
- 假设、推导和未知项明确区分。
- 已有能力和既有行为已检查。
- 高影响问题有负责人和处置结论。

### 系统需求与架构
- 系统需求可以验证并有来源。
- 每条系统需求分配到架构元素或有经批准的不适用理由。
- 接口含义、所有权、有效值和错误语义有定义。
- 重要备选方案、取舍、平台限制和风险有记录。

### 软件需求与实现
- 软件需求来自已批准系统需求和架构分配。
- 代码路径在实际仓库中已确认，不是猜测。
- 任务关联需求和测试，并有依赖与完成定义。
- 实际 diff 没有未经批准的需求或范围变化。

### 验证与收敛
- 验证实际执行，并记录环境、命令、判据、结果与证据位置。
- 每项验收标准有验证证据或正式批准的例外。
- 旧证据如受需求、代码、接口、配置或目标变化影响，须标记失效并重测。
- 所有残余风险、失败、豁免和未解决问题由相应负责人处置。

## 状态不等于证据

任务勾选代表有人声明完成，不代表该工作已被证明。测试文件存在不代表测试通过；构建成功也不证明所有验收条件满足。最终结论必须能追到真实执行记录或正式评审证据。

## 人工审批边界

CLI 的 `--approval REVIEW-ID` 只是存储实际审批记录的引用，不验证审批人身份。产品行为、架构与接口承诺、偏差/豁免、安全和发布等决策仍由项目授权人员负责。


## 双向追溯与规格完备性：可执行检查

```bash
# 检查当前阶段
vsdd trace-check speed-warning

# 预检查即将推进到的阶段
vsdd trace-check speed-warning --stage planned

# 从任意 ID 递归查看上下游追溯链
vsdd trace speed-warning --id FR-001 --direction both
vsdd trace speed-warning --id SYS-001 --direction upstream
vsdd trace speed-warning --id TC-001 --direction downstream

# specified 及后续阶段的 validate 自动执行相同门禁
vsdd validate speed-warning
```

检查失败时命令返回非零退出码，可接入 CI。报告输出各类 ID 数量、阶段覆盖计数和阻塞原因。

- `source-register.md`：将 PRD、会议结论、缺陷、Feature 意图和约束拆成原子义务，逐条登记为 `SRC-xxx`。每一项必须标为 in-scope、out-of-scope 或 deferred；范围内的每条来源都必须连接至少一个 FR。
- `feature-brief.md` 的 `FB-xxx` 代表 Feature；每个 FR 必须同时连回 FB 和来源，并连到至少一个 AC。
- 每个 AC 连接至少一个 SYS；每个 SYS 分配到 `ARCH-xxx` 架构元素，并向下连接到 SWE。
- 每个 SWE 连接实现任务和验证用例；反向检查每个任务是否有来源需求。
- 到 verifying 阶段，每个任务必须映射到真实存在的 `FILE:相对路径`；每个 TC 必须包含实际环境、执行步骤、结果、状态和证据引用。到 converged 阶段，测试必须通过，或有包含 `APPROVAL:` 的正式豁免引用。
- 检查器识别重复/未声明 ID、未知边端点、重复边、证据字段缺失、未连通节点和路径越界。

### 机器检查的边界

脚本可以验证“登记的输入义务与需求 ID 是否都有追溯路径”，但无法可靠判断自然语言语义是否完整表达。因此，在推进到 specified 前，责任人必须审阅 source register 是否穷尽，并填写评审人和真实评审记录。Feature Spec 必须逐项审查 normal、boundary、invalid-input、state-transition、failure、recovery、timing-performance、interface-semantics、safety-security-diagnostics 维度：适用时关联 FR/AC，不适用时说明理由，并留下评审记录。AI 能提示漏项，不能替代语义评审。
